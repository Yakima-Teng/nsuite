# add-utility

## 描述

将外部项目或用户提供的工具方法集成到当前 nsuite 项目中，在保持运行时语义的
前提下完成 JavaScript ESM 实现、JSDoc 类型表达、公共导出、测试和文档更新。

## 使用场景

- 用户要求将其他项目中的一个或多个工具方法复刻到当前项目。
- 用户要求向现有 `lib/Utils*.mjs` 模块添加公开工具方法。
- 新方法包含 TypeScript 泛型、类型别名、品牌类型或类型断言，需要转换为 JSDoc。
- 新方法需要同步对应测试、入口导出和 README 功能清单。

不应触发：

- 用户只要求修改现有方法的业务逻辑，且不新增公开工具方法。
- 用户只要求补充测试、更新 README 或修改 JSDoc。
- 用户要求创建业务模块、服务、页面、命令行程序或新的独立项目。
- 用户只询问 JavaScript、TypeScript 或 JSDoc 的通用写法。

## 指令

### 步骤 1. 确认任务范围

读取并遵守项目规则、本地规则和终端能力记录，再识别以下输入：

- 源文件路径和待迁移的方法名。
- 目标 `lib/Utils*.mjs` 模块。
- 对应的 `test/Utils*.mts` 测试文件。
- `lib/index.mjs` 的公共导出关系。
- README 中与目标模块对应的功能章节。

检查目标文件和测试文件的 Git 差异，识别人类已经完成但尚未提交的改动，不得覆盖、
回退或重新实现这些改动。

**决策分支**：

- **源文件、方法名和目标模块均明确**：直接进入步骤 2。
- **目标模块可根据方法职责唯一确定**：说明判断依据后进入步骤 2。
- **缺少源文件、方法名或存在多个合理目标模块**：提出 1-3 个具体问题，等待用户补齐。
- **源文件无法读取**：停止实施，说明无法读取的路径和所需输入。

### 步骤 2. 分析源方法

逐个分析待迁移方法，记录以下内容：

- 输入、输出和运行时行为。
- 泛型关系、`keyof`、联合类型、品牌类型等静态类型约束。
- 异常处理、序列化失败、空值和边界输入。
- 使用的外部依赖、全局类型或项目专有类型。
- 方法之间的调用和类型依赖关系。

**决策分支**：

- **仅包含标准 JavaScript 运行时逻辑**：保持原始语义直接迁移。
- **包含 TypeScript 类型参数或断言**：删除 TypeScript 专用语法，使用 JSDoc 表达等价关系。
- **依赖源项目的全局类型**：优先在目标模块使用局部 JSDoc `@typedef` 表达；无法等价表达时说明限制，不得静默退化为 `any`。
- **依赖当前项目未安装的运行时包**：先说明新增依赖及影响，获得用户确认前不安装依赖或修改锁文件。
- **发现源方法本身存在疑似缺陷**：默认按源实现复刻并提示风险，不主动改变语义；用户明确要求修复时再调整。

### 步骤 3. 转换实现与 JSDoc

在目标 `lib/Utils*.mjs` 中按现有代码风格添加方法，遵循以下要求：

- 使用 JavaScript ESM 导出，不在 `.mjs` 中写 TypeScript 类型参数、接口、类型别名或 `as` 断言。
- 使用 `@template` 表达泛型，使用 `@typedef` 表达可复用类型，使用 `@param` 和 `@returns` 描述输入输出。
- 必要时使用 JSDoc 局部类型断言连接运行时 API 与更精确的返回类型。
- 为公开方法补充简短用途、参数、返回值和 npm 包导入示例。
- 保持方法命名、参数语义和运行时返回值与源实现一致。
- 只修改目标功能需要的代码，不顺带整理或重构相邻实现。

JSDoc 转换可参考以下形式：

```js
/**
 * @template T
 * @typedef {string & { __brand: "JSONString", __type: T }} JSONString
 */

/**
 * @template {object} T
 * @param {T} obj
 * @returns {Array<keyof T>}
 */
export function getObjectKeys(obj) {
  return /** @type {Array<keyof T>} */ (Object.keys(obj));
}
```

### 步骤 4. 确认公共导出

检查目标模块是否已通过 `lib/index.mjs` 对外导出。

**决策分支**：

- **入口已使用 `export *` 导出目标模块**：不修改入口文件。
- **目标模块存在但入口未导出**：补充与现有排序风格一致的模块导出。
- **新方法未使用具名导出**：修正目标模块导出，不在入口重复列举单个方法。
- **存在导出名称冲突**：停止修改并说明冲突来源，等待用户决定命名方案。

### 步骤 5. 补充测试

在对应 `test/Utils*.mts` 中通过公共入口导入新方法，至少覆盖：

- 每个新方法的主要正常路径和返回值。
- 对象、数组、字符串等与方法职责直接相关的代表性输入。
- 泛型或品牌类型的推断链路，使项目类型检查能够发现类型退化。
- 源方法明确包含的异常或边界分支。

同时检查目标模块中人类刚修改的方法是否引入了未覆盖的行为分支。

**决策分支**：

- **修改新增了可观察的成功分支**：补充对应消息、返回值或状态断言。
- **修改新增了异常回退分支**：构造可稳定触发失败的输入并断言回退结果。
- **现有测试已经覆盖新分支**：不添加重复测试，在交付结果中说明判断依据。
- **测试需要真实密钥、网络或外部服务**：优先使用现有 dry-run、fixture 或可隔离方式；无法隔离时说明限制，不伪造通过结果。

测试应验证公开行为，不绑定无关内部实现细节。

### 步骤 6. 更新 README

定位 README 中与目标 `Utils*.mjs` 对应的功能章节，为每个新增公开方法添加一条简短
说明。

- 保持现有文档语言、列表格式和描述粒度。
- 只更新对应模块章节，不重写其他模块文档。
- 方法未对外导出时不得写入公开功能清单。
- 不手动修改自动生成的 `dist/` 声明或文档产物。

### 步骤 7. 验证改动

先运行与目标测试文件对应的专项测试，再执行项目规定的完整检查命令：

```powershell
node --test test/UtilsType.mts
npm run lint
```

将示例中的测试文件替换为当前目标模块对应的实际路径。

**决策分支**：

- **专项测试或类型检查失败且与本次改动有关**：修复根因后重新执行验证。
- **完整检查全部通过**：进入步骤 8。
- **完整检查因既有代码、外部环境或服务失败**：不得修改无关代码；记录失败命令、测试名称、位置和判断依据，并确保本次专项测试通过。
- **格式化产生任务范围外改动**：识别改动来源，不覆盖人类改动；仅保留本任务必要变更。

验证结束后检查 Git 差异，确认未修改 `dist/`、`node_modules/`、`.git/` 或外部源项目。

### 步骤 8. 输出结果

按以下顺序输出：

1. **风险摘要**：说明兼容性、运行时语义、类型限制或未通过的外部检查。
2. **修改点**：列出新增方法、JSDoc 类型、测试和 README 更新，所有文件引用带路径和行号。
3. **测试结果**：列出专项测试和完整检查的命令及结果。
4. **用户影响**：说明新增公开 API 的用途、导入方式和类型体验变化。

不输出大段已写入文件的完整内容，也不宣称未实际执行的检查已经通过。

## 安全边界

- 不修改用户提供的外部源文件，只将其作为读取和行为对照来源。
- 不修改 `dist/`、`node_modules/`、`.git/`、`.idea/` 或自动生成产物。
- 不覆盖、撤销或格式化掉工作区中已有的人类改动。
- 不为迁移方法顺带修复无关缺陷、升级依赖或重构整个工具模块。
- 未经用户确认，不新增运行时依赖、不修改包版本、不提交或推送 Git 改动。
- 无法确认运行时语义或类型关系时，先说明歧义并询问，不使用猜测实现。
